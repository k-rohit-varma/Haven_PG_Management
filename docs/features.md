# Implemented features

This guide describes behavior currently present in the repository. All requests use `/api/v1`; protected mutations require the CSRF cookie/header pair. ADMIN-only endpoints are also protected on the backend. Business amounts use integer paise and dates use the Asia/Kolkata calendar.

## Authentication and roles

Users sign in with phone or legacy email. Public registration creates TENANT accounts only. Passwords are bcrypt hashed and sessions use an HttpOnly JWT cookie. ADMIN manages account status, roles, owner onboarding, and guarded system administration. OWNER access is scoped by current hostel ownership; TENANT access is restricted to their own application, stay, rent, payments, and deposits. Main endpoints: `/auth/register`, `/auth/login`, `/auth/logout`, `/auth/me`, `/admin/users`, `/admin/users/owners`, `/admin/users/:userId/role`, `/admin/users/:userId/status`.

## Hostels and rooms

OWNER sees and manages only assigned hostels and cannot create properties. Only ADMIN can create a hostel and must select an active OWNER; ADMIN can also reassign ownership with `PATCH /hostels/:hostelId/owner`. Reassignment is audited and notifies both owners. Hostel edits and soft deletion use `PATCH /hostels/:hostelId` and `DELETE /hostels/:hostelId`; deletion is blocked while occupants remain. A deleted hostel can be restored through the ADMIN restore endpoint.

Hostel detail includes aggregate inventory counts and a server-paginated room list. OWNER manages rooms only under assigned hostels; ADMIN can open any property's room list. Room filters combine search, gender eligibility, sharing type, capacity, default-rent range, minimum free beds, availability, and active state. Sorting supports numeric-aware room identifiers, rent, free beds, occupancy, and creation time. Rooms support create, edit/status change, soft delete, and configuration history through `/hostels/:hostelId/rooms`, `/rooms/:roomId`, and `/rooms/:roomId/history`. Capacity cannot fall below occupancy, eligibility must match the hostel policy and occupants, and occupied rooms cannot be deleted. Default rent changes affect future assignments and do not rewrite a stay's agreed rent. ADMIN can block and unblock a hostel; owner and tenant access is denied while blocked, with historical stays and financial records preserved.

## Applications, assignment, and stays

TENANT can discover active eligible hostels even before a room is available and apply to different hostels; duplicate pending applications to the same hostel are prevented. Owners/ADMIN can approve an application without assigning a room or use `/tenant-applications/:applicationId/approve-and-assign` to approve and assign atomically. Room cards link to the approved-tenant assignment workflow. The assignment dialog shows tenant/property/room, room default rent, and a separately editable agreed monthly rent, deposit, and move-in date. Room details return only occupant names to tenants and operational occupant details to the assigned owner/admin. Tenant rent dues reference the stay and use its effective rent terms. Tenants can request rent and room changes; decisions are audited, and room transfers preserve the stay and its rent/payment history. A tenant can cancel a pending application. Owners can mark a tenant as left; past stays remain available, and returning tenants receive a separate stay record.

## Rent, payments, deposits, and rent changes

Rent dues are generated by the protected scheduler endpoint `/jobs/generate-rent-dues`; there is no in-process timer. Dues are monthly, anchored to move-in day, and generation is idempotent. TENANT submits payment records; OWNER/ADMIN approves or rejects. Only approved allocations settle dues, partial payments are supported, and prior payment decisions remain in history.

TENANT may request a rent change for an eligible future cycle. OWNER/ADMIN decides; approval appends an effective-dated rent term without rewriting prior dues. Deposit receipts, refunds, deductions, and adjustments are separate per-stay ledger entries and never automatically offset rent.

## Notifications and audit logs

Authenticated users can list their own notifications and mark one or all read using `/notifications`. Recipient scoping is enforced in queries. Notifications are emitted once per application/payment/rent decision and hostel-owner reassignment using a unique event key. The dropdown closes on outside pointer interaction or Escape.

Audit logs are available only to ADMIN through `/admin/audit-logs` and `/admin/audit`. Sensitive account, ownership, room, financial correction, and decision workflows record audit entries. OWNER and TENANT cannot access audit data through the API.

## Search, pagination, and themes

Hostel listings, user administration, payments, rent dues, audit records, and other list APIs use backend filters/pagination where implemented. Property, user, and rent-due search wait 1,500 ms after typing; server request sequencing prevents older responses replacing newer search results. Fixed-size selectors used to complete a workflow are not search results.

The authenticated layout toggles Light and Dark themes and persists the preference in `localStorage`; startup applies it before React mounts. Login/registration share the saved document theme. Dark styles cover main panels, tables, forms, dialogs, dropdowns, and navigation.

## Known limitations

- No room-assignment timer UI/component exists in the checked-out source, so a reported timer crash cannot be reproduced or fixed here. Rent generation is an external scheduled API call.
- Integration workflows requiring MongoDB transactions need an isolated replica-set test URI. These tests are skipped when `TEST_*_MONGODB_URI` is absent.
- The theme styling is implemented in the shared stylesheet; manual visual review across all pages/devices remains useful.
